---
title: pgvector
description: Reference for the pgvector adapter, which wraps a pg Pool or Client and compiles filters to JSONB predicates.
---

The pgvector adapter wraps any client with a `query(text, params)` method that resolves to `{ rows }`. A `pg` Pool or Client works as is. An index is a table.

```ts
import { Pool } from "pg";
import { createPgvectorStore } from "vecstore-sdk/pgvector";

const store = createPgvectorStore({
  client: new Pool({ connectionString }),
  schema: "public",
});
```

Install the client alongside the SDK:

```bash
bun add vecstore-sdk pg
```

For postgres.js, wrap `sql.unsafe` so it resolves to `{ rows }`, and pass `{ query: async (text, params) => ({ rows: await sql.unsafe(text, params) }) }` as the client. The test suite does not run against postgres.js.

## Table layout

`createIndex` runs `CREATE EXTENSION IF NOT EXISTS vector`, creates the table below, and adds an HNSW (Hierarchical Navigable Small World) index for the metric and a GIN (Generalized Inverted Index) index on `metadata`:

```sql
CREATE TABLE "docs" (
  id text NOT NULL,
  namespace text NOT NULL DEFAULT '',
  embedding vector(1536) NOT NULL,
  metadata jsonb NOT NULL DEFAULT '{}'::jsonb,
  PRIMARY KEY (namespace, id)
);
```

`CREATE EXTENSION` needs a role that can create extensions. If your application role cannot, create the extension yourself before you call `createIndex`.

An index name can be at most 49 bytes, so that the `_embedding_idx` and `_metadata_idx` index names stay under the 63-byte Postgres identifier limit. `createIndex` returns `invalid_argument` for a longer name.

## Metric detection

Queries read the metric from the HNSW or IVFFlat index definition in `pg_indexes`. When no index exists, they default to cosine. This also works for tables the SDK did not create.

The store caches the metric per table after the first query and forgets it when `createIndex` or `deleteIndex` on the same store touches that table, or when a query on that table fails. If another process recreates a table with a different metric, create a new store.

`listIndexes` returns the tables in the schema that have an `embedding vector` column.

## Filtered and large queries

pgvector applies the namespace and the filter after it scans the HNSW index, and a scan stops at `hnsw.ef_search` candidates, 40 by default. Without an iterative scan, a query with a `topK` above 40, a selective filter, or a namespace that holds part of the table returns fewer than `topK` records. On pgvector 0.8.0 or later the adapter turns on an iterative scan for each query, so the scan continues until `topK` records pass. It sets `hnsw.iterative_scan` to `strict_order` for that one statement and keeps a value you set yourself, such as `relaxed_order` on the database.

On an older pgvector there is no iterative scan and the adapter sends the plain statement. Upgrade the extension, or raise `hnsw.ef_search` for the role or the database. A filter that matches few records can still return fewer than `topK` records on any version, because pgvector stops an iterative scan after `hnsw.max_scan_tuples` tuples, 20,000 by default. The adapter also sends the plain statement to a table with an IVFFlat index, which the SDK never creates.

## What the adapter stores

| Concern   | pgvector                                    |
| --------- | ------------------------------------------- |
| Index     | Table                                       |
| Namespace | `namespace` column, part of the primary key |
| Id        | `id text`                                   |
| Metadata  | `metadata jsonb`                            |
| Metric    | Read from the HNSW index operator class     |
